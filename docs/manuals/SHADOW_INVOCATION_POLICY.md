# 影子记忆调用策略与读取路径轮换

日期：2026-10-07。状态：**生效**（阶段 1 = 并行比较已开启）。范围：何时自动调用 los-memory 影子、何时不该调、以及把读取从 Nowledge 轮换到影子的分阶段做法。

配套：[影子运行手册](SHADOW_MEMORY.md) · [P0 评测基线](../reports/2026-10-07-eval-baseline.md) · [就绪度复核](../design/nowledge-replacement-readiness.md) · [分阶段路线图](../design/memory-roadmap.md)。

---

## 1. 判据：影子是什么，因此什么时候用它

影子是**单一 space、只读、可重建、确定性的字面索引**（2,048 条 default space durable 记录）。它自动调用划算，当且仅当满足以下之一：

- **查询里有字面锚点**：UUID、短/长哈希、路径、文件名、错误码、版本号、主机别名；
- **要的是完备性而不是概念召回**：字面匹配会返回**全部**候选，语义检索只给 top-K；
- **主库慢或不可用**：影子在 M3 本地，主库是 node34 的 HTTP + MCP。

依据来自 40 例评测（`--scope native`，35 计分例）：

| 查询形态 | 影子 Hit@5 | Nowledge 默认搜索 | 结论 |
| --- | --- | --- | --- |
| 精确标识（`SQLITE_IOERR_TRUNCATE`、路径、短哈希） | **1.000** | 0.200 | 影子优先 |
| 2–4 字中文短词 | **0.800** | 0.000 | 影子优先 |
| 概念/改写问句 | 0.000 | 0.000 | **两边都不行**，不要用它决定分流 |
| 按项目隔离 | 1.000，跨项目违规 **0** | 0.200，`no_answer` 类 2 条违规 | 影子优先（且更安全） |

**成本模型（这决定了能不能"自动"）**：Nowledge 的 prompt-time recall 曾被 profile 关掉，理由是 `nmem memories search` 实测**每轮 12.8–13.0 s**；影子的字面检索是**索引路径 1.1–2.2 ms**、经 SSH MCP 往返中位 **30.5 ms**。便宜约两个数量级——这是影子能承担自动调用、主库不能的原因，也是本策略**绝不在关键路径上同步调用主库**的原因。

## 2. 路由规则（确定性，不用 LLM）

```
含字面锚点(regex)          → 影子优先；空结果再问主库
含 ≤4 字 CJK 词           → 影子优先；空结果再问主库
其余（概念/改写）           → 主库优先；影子只用于否决复核
命中多类                   → 先影子（便宜），主库结果为准
```

分类器实现为 `memory_tool.shadow.classify_query`，纯正则、无副作用、可审计——**故意不用 LLM**，否则阶段 1 的分歧数据无法解释。实测在 40 例上：`exact_identifier` 5/5 → `literal_anchor`，`chinese_short` 5/5 → `short_cjk`，`semantic_paraphrase` 5/5 → `conceptual`。

注意**查询形态 ≠ 任务类别**：`project_isolation`、`fact_revision`、`cross_tool_continuation` 这三类是"任务"而不是"问法"，会散落在不同形态里。路由按**问法**，分歧统计也按问法。

## 3. 新鲜度前置（配置可用 ≠ 镜像可用）

照 `~/.codex/AGENTS.md` 里 codebase-memory-mcp 的成熟范式：**先验健康与新鲜度，再依赖结果**。

- 调用前看 `shadow_status`（或结果里的 `verified_at`）；把 `sync.finished_at` 当 as-of，**不要当当前事实**。
- 当前轮转语义：2,048 条 × 100 条/轮 × 300 s ≈ **102 分钟全量轮转**，所以单条记录可能最旧约 1.7 小时。
- 看到 `search_index.state != "ready"`、`meta.mode == "scan"` 或 `meta.scan_terms` 非空 → 该次结果**降级**，把它当"不完整"而不是"没有"。

## 4. 回退规则（写死，避免"重试不可用路径"）

| 情况 | 动作 |
| --- | --- |
| `shadow_status` 报 `unresolved_errors` / `search_index.state=not_built` | 立刻回主库，**本任务内不再重试影子** |
| 结果为空但查询是概念型的 | 这是预期行为（影子本就无语义），直接问主库，**不要**反复改词重试 |
| 结果为空且查询有字面锚点 | 先用 `shadow_get` 按 ID 直取复核一次；仍无 → 回主库 |
| 项目过滤后为空 | **不等于**"该项目没有记忆"：看 `meta.coverage`（当前 557/2,048 明确归属），再决定是否回主库 |
| 影子比主库慢或不可达 | 回主库；影子只是加速与对照，不是可用性依赖 |

## 5. 阶段 1：并行比较（**已开启**）

目标不是换答案，而是**采集真实分歧**——这条 lane 此前从未有过真实对照调用。做法：

1. 在你正常的记忆检索之外，**额外**调用 `shadow_compare(query)`。
2. 它**立刻**返回影子侧（毫秒级），并把同一个 query **入队**；**不**同步调用主库。
3. M3 上的 `co.los.memory-shadow-compare-drain`（每 15 分钟）把队列里未缓存的 query 拿去问主库，写成一条分歧记录。单次上限 8 个未缓存查询（每个约 13 s），带 24 h query 缓存，跑不完的下轮继续。
4. **答案仍然来自主库。** `shadow_compare` 是仪表，不是答案源——工具描述与 `initialize.instructions` 都写明了这一点。

查看分歧：

```sh
ssh m3-t 'cd ~/.local/share/los-memory-shadow/releases/<release> && \
  ~/.local/bin/python3 -m memory_tool.shadow compare-report'
```

`compare-report` 按**查询形态**聚合 `mean_jaccard` / `shadow_only` / `nowledge_only`。读法：

- `shadow_only > 0` 且 `jaccard` 低 → 影子补上了主库默认搜索漏掉的候选（这正是要量化的收益）。
- `nowledge_only > 0` → **风险侧**。注意结果集大小不对称（影子可能只返回 3 条，主库返回 5 条）会人为压低 jaccard，**必须把两侧 `limit` 对齐后再下结论**。
- 主库查询失败时**不写分歧记录**（否则会把失败伪装成"一致"），并在输出里报 `errors`。

首条真实数据（`los-memory 双轨`，short_cjk，limit 5）：影子返回 3 条（含"批准双轨验证"与部署记录），主库返回 5 条完全不同 ID，overlap 0 —— 影子命中的是主题精确的记录，语义检索给的是弱相关记录。样本量 1，只作示例，不作结论。

## 6. 阶段 2/3：按形态分流 → 扩客户端

**前置**：阶段 1 攒够每个形态的样本（建议每形态 ≥30 条真实查询）再定边界。

| 阶段 | 动作 | 通过判据 | 回退 |
| --- | --- | --- | --- |
| 2a | 单客户端（DSH）按路由表分流 | 分流后答案质量不降（人工抽检 ≥20 条）、`nowledge_only` 未造成漏答 | 删该客户端 MCP 条目 |
| 2b | 扩到 Codex/Kimi/Grok（均已接入） | 同上，逐客户端独立验收 | 同上 |
| 3 | 影子成为字面类的**默认**入口 | 门槛 1（14 天）与门槛 2（评测）同时满足 | 同上 |

**这一层之所以是"平滑"的**：影子只读，回退 = 摘掉同一个 MCP 条目；主库全程是唯一写入方，**没有任何数据迁移**。这是四层轮换里唯一可以随时无损来回的一层。

## 7. 第 1 层：同步参数轮换（尚未执行）

现状 300 s / 100 条/轮 → 轮转 102 分钟；提案 **每小时清单 + 每 15 分钟 100 条** → 轮转 5.1 小时、字节约 **−90%**。

**为什么还没切**：按批准的计划先攒 24 h 计量基线。基线在 `sync_runs` 表里自然累积，当前实测：

| 指标 | 实测 |
| --- | --- |
| 观测间隔 | 298.4 s（即节奏正常） |
| 单轮字节 | **5,682,839 B ≈ 5.42 MiB** |
| 预计日流量 | **≈ 1.53 GiB/日** |

**切换（一条参数、可回退）**——改 M3 plist 的 args 加 `--manifest-cache-seconds 3600`，然后 `launchctl bootout && bootstrap`。回退就是把该参数改回 `0` 再 bootstrap；**数据库不用动**（清单缓存只是 `state` 表里的一个键）。

⚠️ **必须先认的取舍**：开了清单缓存后，**新记录与删除的发现延迟从 ~5 分钟变成 ≤1 小时**，正好卡在门槛写的"fallback 新记录发现 ≤1 小时"边界上。建议清单周期取 **30 分钟**留余量，或明确接受这个边界。

切换后 24 h 的判据：`oldest_verified_at` ≤24 h（预期 ≤5.1 h）、`metering.errors = 0`、字节下降 ≥70%。告警已覆盖这些条件（`sync_silent` / `sync_errors` / `stale_verification`）。

## 8. 第 4 层：主库轮换（现在做不到"平滑"，别假装可以）

**原因**：没有写入路径（迁移门槛 5）。只读镜像无论怎么切都不构成主库。

真到那时，可逆的关键**不是切 URL**，而是切换后新库产生的写入必须能导出并按 `(space, source_id)` 规范映射回灌旧库，否则"切回去"会丢新数据（见 [memory-roadmap.md](../design/memory-roadmap.md) §8 P6）。现在能做的准备：持续记录身份摘要（`shadow summary`），将来对账才有基线。

## 9. 明确不要做的

- 不要用评测里 0.771 vs 0.200 的**总分**定分流边界——用例是照语料写的，有循环性（[基线报告 §6](../reports/2026-10-07-eval-baseline.md)）。能站住的只有"字面 vs 概念"这个**形态判断**。
- 不要同步调用主库做比较（13 s/次，正是 profile 关掉 prompt-time recall 的原因）。
- 不要把影子结果当当前事实：它带 as-of，最旧可达约 103 分钟。
- 不要在影子报降级时继续依赖它；也不要因为一次空结果就重试同一路径。
- 不要把"过滤后为空"读成"没有记忆"。
