# Current State

This document records the current, implemented state of `los-memory`.

## Isolated Nowledge shadow (updated 2026-10-07)

- `memory_tool.shadow` mirrors default-space durable records through canonical Nowledge REST reads; stores source IDs, snapshots, hashes, revisions and refresh attempts in a separate private SQLite database.
- `memory_tool.shadow_mcp` exposes `shadow_search`, `shadow_get`, `shadow_status` and `shadow_compare` over stdio; all four are read-only. Search is literal substring matching; `shadow_search` returns `{results, meta}` where `meta` names the index path per term (`trigram` / `bigram` / `scan`), the uncovered terms, and the coverage behind any filter. `kind` filters on the mapped `unit_type`; `claim_status` is `undeclared` when the source has none.
- Read-path rollover phase 1 is **on**: `shadow_compare` answers the shadow side immediately and queues the query; the M3 job `co.los.memory-shadow-compare-drain` (every 900 s, max 8 uncached lookups per run, 24 h query cache) queries the primary off the critical path and appends to `compare-results.jsonl`. `shadow compare-report` aggregates divergence by query form. The primary is never called synchronously in a comparison path because `nmem memories search` costs a measured ~13 s. Policy: `docs/manuals/SHADOW_INVOCATION_POLICY.md`.
- The compare ledger resolves from the **served database's directory** (`PRAGMA database_list`), not from the process default, so pointing the MCP at a fixture database keeps its queue beside that fixture; an explicit `state_dir` still overrides. Phase 1 has collected 1 sample so far — the gap is adoption, not plumbing: no real `shadow_compare` call has been made since the instrument went on.
- A record the source reports as gone is deactivated but kept, and is re-probed at most once per `TOMBSTONE_RECHECK_SECONDS` (24 h) rather than every rotation; each run reports `tombstones_deferred`. Deletions are still discovered by the manifest.
- **Repository vs deployed release (verified 2026-10-14).** The running M3 service is aligned with the repository: release **`b366080b3d4aa630ab19`** equals the `memory_tool/**` tree at the current `main`, and **five** launchd jobs plus the `serve` launcher point at it — `co.los.memory-shadow` (sync, 300 s), `-compare-drain` (900 s), `-recall-probe` (6 h), `-maintenance` (rotatelog), and `-compact` (weekly, added 2026-10-14). Re-running the deploy on the same tree is idempotent and reports every sibling `changed: false`, which is also how the new job is kept from drifting. (An earlier release the same day, `9934bc20a2cca2b86e43`, was superseded within the hour when `--vacuum` gained its truncate checkpoint; the second deploy moved all five jobs in one step.) Earlier the same month this was **not** true — on 2026-10-10 the live release was `7aaac3fcd55fffe2a143` (= code at `545f0e7`, 11 commits behind in `memory_tool/shadow.py`) and `maintenance` pointed at a third, older release; in that window the deployed code lacked `TOMBSTONE_RECHECK_SECONDS`, `recall_probe` and the compare-ledger path fix, so tombstones were re-probed every rotation and the report's per-day `missing` count inflated 0 → 33 → 129 → 440 → 1229. `scripts/deploy_shadow.py` scans `co.los.memory-shadow*.plist` and rewrites each job's own `WorkingDirectory`, so that three-way drift can no longer arise. Evidence: `docs/reports/2026-10-10-shadow-14day-formal.md` §16.2 and `docs/reports/2026-10-14-status-review-and-optimization.md` §3.6.
- **Space is a two-lever problem, and both levers are now wired (2026-10-14).** `shadow reindex` ends with an FTS5 `optimize`, so a full rebuild no longer leaves a stale generation of segments behind — that is what had taken the live file from 69.7 MiB (after the approved 2026-10-10 `VACUUM`) to 194.8 MiB in four days while records grew by only 25. `status.storage` reports `freelist_bytes` **and** `fts_index_bytes`, because the dominant waste was dead segments inside the live index, invisible to the freelist. A weekly `co.los.memory-shadow-compact` job runs `compact` (optimize only, measured 0.3 s); `VACUUM` stays explicit by policy, so **the file only shrinks when someone asks**. `compact --vacuum` also ends with a TRUNCATE checkpoint, because `VACUUM` pushes every page through the WAL and leaves it allocated at roughly the size of the whole database — measured on the live mirror, the first `--vacuum` produced a 73.9 MiB database next to a 74.3 MiB `-wal`, i.e. a command reporting 124.3 MiB reclaimed while ~74 MiB of it was still held. Measured end state 2026-10-14: `compact --vacuum` returned 124.3 MiB (204,210,176 → 73,908,224 B) plus a second pass returning the 1.4 MiB re-allocated by the following sync round, `fts_index_bytes` 106.9 → 20.1 MiB, `-wal` 0, `integrity_check = ok`, and every row count unchanged.
- `shadow recall-probe` detects what the existing alerts structurally cannot: a primary that reports `Search Index: Ready` while content written after some point is unretrievable. It takes rare literal anchors from the mirror and asks the primary for them, in three groups — `recent` (the signal), `control` (the oldest records, proving the primary answers at all) and `span` (evenly spaced, locating the boundary). The verdict compares `recent` against `control`; the `*_created_at` fields are indicative only and `created_at` is not index-ingestion order. Read-only on both sides; each probe costs the primary ~13 s, so it is a scheduled job, never a read path. **Since 2026-10-10 it runs as the M3 job `co.los.memory-shadow-recall-probe`** (`StartInterval=21600`, i.e. every 6 h, output `recall-probe.out.log`). **Its 2026-10-08/10-10 verdict was a false red, corrected 2026-10-13 (`4cc702f`).** The probe used to run `nmem memories search <id>` and treat "the id is among the hits" as retrievable: that holds for import-era records whose id is a UUID (5/5 measured) and never for the `sha256:<hex>` ids our own write path creates (3/3 missing from their own hits), so it measured its own lookup method rather than the primary's health — every one of those records was readable via `GET /memories/<id>` with HTTP 200. The criterion is now a by-id fetch (`nmem memories show <id> -j`), and a failure that is *not* "not found" (missing CLI, transport error) is reported through the error channel and falls back to the anchor search, because "cannot tell" must not read as "content lost". Live since the fix: `verdict = ok`, `recent_rate` 1.0 (6/6), `control_rate` 1.0, `newest_retrievable_created_at` = the newest mirror record, and the high alert cleared at 2026-10-13 13:14. The `2026-10-10` claim that the primary's coverage of recent writes is "partial and unpredictable" rested on that broken criterion and is **withdrawn**; what remains is the narrower, independent observation that primary semantic search is sensitive to query form. Evidence: `docs/reports/2026-10-14-status-review-and-optimization.md` §4. **The verdict is alarmed**: `scripts/shadow_report.py` raises `primary_stale_projection` (high) when the newest probe says `stale_projection_suspected`, and `recall_probe_stale` when the 6 h job stops producing results (a silent instrument is itself the finding). `evaluate_alerts` requires the probe state — passing `None` raises, so a caller cannot silently skip the only threshold that looks outside the mirror. Delivery is configured: the alert job pushes to the Uptime Kuma monitor `los-memory-shadow-alerts` (push type, 3 h heartbeat), whose `FeishuBridge` notification forwards through the existing `kuma-webhook-bridge` -> `feishu-push.sh` chain, and the write side self-caps its own ledger (`cap_ledger`, 8 MiB / keep 5) so `alerts.jsonl` is bounded. A push monitor is used rather than a plain webhook so that a *stopped watcher* is also detected — the measured 2026-10-10 failure was exactly that (four silently missed hourly runs while M1 slept). See `docs/manuals/SHADOW_MEMORY.md` and `docs/reports/2026-10-10-shadow-14day-formal.md` §8.3/§16.3.
- Derived structures are `records_fts` (FTS5 trigram), `cjk_bigrams` (2-character CJK, which trigram cannot serve), `record_facets` / `record_labels` (kind/project/claim_status/source_app) and the `sync_runs` / `sync_errors` metering ledgers. All are rebuildable from `records` with `shadow reindex`; an index that was never built reports `search_index.state = not_built` instead of answering "no memories". `shadow reindex` ends with an FTS5 `optimize` because it is itself what invalidates the index: it deletes every `records_fts` row and re-inserts them, and FTS5 keeps the deleted terms as tombstones until segments are merged. Measured 2026-10-14, two rebuilds (the 10-10 and 10-13 deploys) had left ~90 MiB of dead segments inside the live index — invisible to `freelist_bytes`, because those pages count as used until the merge. `status.storage` therefore also reports `fts_index_bytes` (index payload summed from the FTS5 shadow table; `dbstat` is a compile-time option so it cannot be relied on, and this is a payload measure to compare against itself over time, not page accounting). `shadow compact [--vacuum]` stays the explicit space lever; it is not scheduled.
- `project` is **not** a Nowledge field: 0 of 2,457 mirrored records carry `metadata.project`. It is assigned only from a registered label (`memory_tool/shadow_registry.py`) or an explicit `metadata.project` declaration, else `unassigned` — measured 2026-10-14: 622 / 2,339 active records (26.6%) assigned, with 23 records marked `multi` because they genuinely carry two registered project labels. Filtering is label-set membership, so a `multi` record is still found under each of its projects.
- M3 runs a launchd refresh every 300 seconds, at most 100 records per invocation; the initial baseline used an explicit larger batch. This is a rotating refresh, not a five-minute freshness guarantee for every record. `sync --manifest-cache-seconds N` (default 0 = unchanged production behaviour) can decouple the full listing from the per-record refresh for a measured traffic reduction.
- Nowledge remains the only formal write target. Raw conversations, Working Memory generation, learned semantic retrieval and primary-write migration are not implemented in the shadow.
- Core auto search falls back to LIKE on no FTS match; metadata filters apply to hash-vector ranking; mixed embedded/unembedded records are included; deduplication scopes to project and kind; content edits invalidate old embeddings and refresh content hashes.
- See `docs/manuals/SHADOW_MEMORY.md`, `docs/reports/2026-10-07-shadow-search-index.md` and `docs/reports/2026-09-26-dual-track.md` for operation and validation boundaries.
- **Client availability is per profile, and currently uneven (verified 2026-10-14).** The shadow MCP is configured only in the DSH `web` profile (`~/.dsh/profiles/web/cordis.patch.yml`); the `desktop` profile that serves the current GUI session has none (its only MCP is `mcp-los`), so `shadow_search` / `shadow_get` / `shadow_status` / `shadow_compare` are not on the tool surface there and `AGENTS.md`'s "literal anchor, call the shadow first" cannot be executed in such a session. The server side is healthy — a manual stdio handshake returns `serverInfo los-memory-shadow v0.1.0` with all four tools, and the 2026-10-10 reconnect hardening holds (11 reconnects since, deepest attempt 6/1000000, none exhausting the budget). This, not agent adoption, is why the phase-1 compare ledger still holds a single sample.

## Memory console and detection coverage (added 2026-10-14)

- `scripts/memory_console.py` is the **one place that shows the whole memory system**, and the only thing that checks all of it. `report` (default) prints a human view or `--json`; `alert` evaluates thresholds, records to its own capped ledger (`memory-console-alerts.jsonl`) and notifies. It reads four surfaces:
  - **shadow mirror** — delegated to `scripts/shadow_report.py`'s readers (status, recall probe, backup ledger), so "how to read the shadow" exists once;
  - **primary (Nowledge)** — `nmem status/stats/feed inbox`, which had never been checked on a schedule;
  - **write path** — the hourly `mem-sync-evolve.py` log (last run's `created/updated/skipped/failed` plus its age), never read by anything before;
  - **local profiles** — row counts, newest record and size for `codex`/`claude`/`shared`, plus a snapshot so *growth* is visible. These are legacy stores, so growth is the signal: the test suite that appended 18 rows to `shared` on every run was invisible precisely because nobody looked at a row count over time.
- Alert codes (`memory_console.py alert`): `shadow_alert_stale` (the hourly shadow watcher itself has gone quiet — the one thing the shadow report cannot report about itself), `primary_cli_missing`, `primary_unreachable`, `primary_unhealthy`, `primary_embedding_degraded`, `primary_reviews_pending` (escalates inside a 7-day expiry window, because the primary discards an unattended review silently), `primary_review_backlog`, `memory_write_path_missing`, `memory_write_path_stale`, `memory_write_path_failed`, `local_profile_growth`. Each has a test that fires it, plus a healthy baseline that must produce nothing.
- **Delivery is the direct Feishu path** (`~/.dsh/scripts/feishu-push.sh --key ...`), the same one `disk-cleanup.sh --push` uses, not the Uptime Kuma monitor. Measured reason: Kuma's *notification text* carries only the monitor name, so console findings would arrive as "不可用：los-memory-shadow-alerts" about a healthy shadow, and correcting that name needs a container restart that would blip six 60-second monitors. The `--key` is `memory-console-<date>-<codes>`, so the same findings do not repeat every three hours while a changed set is a new message, and a cleared set sends one recovery notice.
- The watcher runs as M1 launchd job `com.echerlos.memory-console-alert` (`StartInterval=10800`, i.e. every 3 h — inside the write path's 6 h staleness budget). It sets `PATH` explicitly: launchd's default excludes `/usr/local/bin`, so the very first run reported a healthy primary as unreachable (`primary_cli_missing` now exists to keep that mistake from recurring).
- **In-session view (added 2026-10-14)**: the DSH plugin `dsh-memory-console` (source: `~/syncfolder/project/dsplugins/dsh-memory-console`) adds a 「记忆」 tab to the DSH conversation view. Its host half registers one read-only endpoint, `GET /plugins/dsh-memory-console/status`, whose `mode=full` runs exactly the script above (`report --json`) — the tab holds no memory logic of its own, so the UI cannot disagree with the alert job. `mode=fast` answers from the ledger and snapshot only. It is installed in the **desktop** profile (app-managed; the CLI refuses that profile, so the dependency and bundle entry were added the same way the app does it — pnpm run from the app's own runtime), and needs a host restart to load.
- **Known residual**: this job's own silence is not independently alerted (a dead watcher cannot report itself, and the Kuma monitor belongs to the shadow watcher whose name it carries). Its ledger and run history are the evidence that it ran; a second Kuma monitor or a rename would close it and needs a restart decision.

## Current Architecture Notes

- The active CLI path is implemented in `memory_tool/cli.py`
- The active observation CRUD path is still served from `memory_tool/operations.py`
- `memory_tool/core/` is now a compatibility layer that forwards historical imports to the active top-level modules
- New development should target the top-level `memory_tool.*` modules rather than `memory_tool.core.*`
- Active session state is now bound to the current database path, so profile-level session files do not leak session state across different SQLite databases
- `admin doctor` performs read-only diagnostics and does not create a missing database file as a side effect of health checks
- `Observation` records now persist structured `metadata`, and `observation add/edit`, `memory get`, and `memory export` preserve that metadata round-trip
- `observation bulk --input <json|@file|@->` supports multi-item writeback from inline JSON, files, or stdin
- `Feedback` records now also persist structured `metadata`, and both `observation feedback` and `review apply` propagate it into feedback history
- `memory search` and `memory list` support metadata-native equality filters via `--metadata-filter`
- Search treats user text literally: `%` and `_` in a query match themselves, not as LIKE wildcards (via `escape_like` / `like_pattern` in `memory_tool/utils.py`, paired with an explicit `ESCAPE '\'` clause)
- `memory search` retries a **single-term** query as a quoted FTS phrase (`_fts_query_candidates` in `memory_tool/operations.py`). FTS5 gives `-`, `/`, `.` and `:` operator meaning, so path/filename/identifier queries used to raise `sqlite3.OperationalError` — swallowed in `mode="auto"` into a full-table LIKE scan (100% of identifier queries carrying those characters, ~20x the indexed latency) and surfaced as a raw SQLite error under `--mode fts`. A quoted phrase is matched as adjacent tokens, so it stays indexed and is separator-agnostic (`foo/bar` also finds `foo-bar`). Multi-word queries are deliberately not quoted, because that would turn FTS5's implicit AND into an adjacency requirement; `--mode fts` still raises when every form fails. The ranking effect is **mixed and inside noise** at n=80, so this is a latency/error fix, not a ranking improvement — whether literal containment should outrank a separator-variant match is still open (`TODO.md`)
- `mode="auto"` still tokenizes an identifier such as `los_memory` into `los` + `memory`, so a query whose literal appears nowhere can still return token matches. Sampling 80 unique-identifier queries per separator group put the ranking effect of the quoting change at Hit@1 0.775 → 0.812 (underscore) and 0.887 → 0.863 (other separators) — mixed, within noise, and far smaller than the single `los_memory` example first suggested
- `memory search --semantic` is a **deterministic lexical-overlap re-ranker over the literal candidate set**, not a learned embedding and no longer a full-table scan: it hashes tokens into 32 dimensions (with 2-character windows for runs of Han characters) and re-ranks only what the literal path returns, within an explicit `candidate_limit` (default `max((offset+limit)*10, 100)`). Measured 2026-10-10 on the real ledger (5,919 observations, `scripts/measure_core_search.py --family both --samples 30`): p50 **994 ms → 14.3 ms** (cjk) and **1000 ms → 0.7 ms** (identifier), i.e. from ~68x the literal path to parity with it. Quality on identifiers went **Hit@1 0.267 → 0.73–0.83** (three runs), far outside the ±0.067 run-to-run spread measured on the `auto` control at n=30; on cjk it is **no regression** (0.767 before and after — a single-run comparison of that size is inside the noise). A query with no literal candidate now returns empty, which is the honest answer for a lexical re-ranker: the old scan ranked thousands of ~0 similarity rows and returned noise. `auto` therefore remains the default, and no retrieval-quality claim should be made without re-running the instrument.
- Core retrieval quality is measured by `scripts/measure_core_search.py` — rarity-controlled Hit@K over two families (`--family cjk|identifier`, the latter because FTS-parsing changes are invisible to CJK windows) plus `--self-check`, which is a CI step. `tests/unit/test_core_search_quality.py` is the CI-able gate and fails if `--mode` stops defaulting to `auto`
- `--profile` is a storage-partition selector only; tenant/user/request/trace identity belongs in structured metadata rather than profile naming
- `HubLiteSession` (hub-lite cross-repo control-plane records) resolves its database as explicit `db_path` -> `MEMORY_DB_PATH` -> the `shared` profile. It deliberately does **not** follow `MEMORY_PROFILE`: the hub-lite ledger is shared across repos, so following a per-agent profile would split it. The env override exists so a caller can run without touching the operator's real ledger
- The current stable smoke contract for upstream runtime verification is `review apply --file ... --dry-run`, `admin manage stats`, and `observation delete --dry-run`

## P2-01 service contract layer (added 2026-10-11)

- `memory_tool/service_contract/` holds the **P2-01 contract layer** for the future write path: a versioned application contract (`CONTRACT_VERSION`), five versioned wire schemas with a dependency-free validator, receipt/outbox semantics, the identity and authorization model, and an in-process reference adapter. It is a contract, not a runtime.
- Nothing in the running tool reaches it: `memory_tool` and `memory_tool.cli` do not import the package, no CLI command exists, no database file is created, and the package imports no `argparse`/`socket`/`http`/`urllib`/`sqlite3`. `service.sqlite3` is **declared** (tables, columns, migration version, DDL) but never created here.
- The N1-N11 negative tests were written before the implementation: the first run failed at collection (`ModuleNotFoundError: No module named 'memory_tool.service_contract'`), and the file's 44 cases are green now. Deferred parts are named per test: real multi-device outbox replay and real Kimi/Codex/Grok writes remain P2-03; the isolated SQLite runtime, projections and cache expiry remain P2-02, which still waits on the P0 exit condition.
- Semantics worth knowing before reading any future write-path code: `accepted` means only that the original payload is durably stored (`lexical_ready`/`semantic_ready` stay false and are reported as the named degradation `projections_pending`); replaying the same `(principal, client_event_id)` returns the same receipt, while a different payload under the same key is refused as a conflict; server-owned identity fields are refused rather than stripped; `effective_scope = requested ∩ granted`; only an evidence-bearing approval can reach `asserted` and `claim_status` otherwise stays `undeclared`.
- Evidence: `docs/design/p2-01-contract-layer.md`, `tests/unit/test_service_contract_negative.py`, `tests/unit/test_service_contract_contract.py`.
